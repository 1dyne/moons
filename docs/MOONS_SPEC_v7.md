## 1. 제품 정의

**노션과 옵시디언이 "저장한 것"의 지식 베이스라면, MOONS는 "아는 것"의 지식 베이스다.**

- 모든 노트와 개념은 **앎의 상태**를 가진다. 저장된 순간 끝나는 것이 아니라, 정리되고 확인되고 설명할 수 있게 되는 변화가 기록된다.
- MOONS AI(이하 MOONS)는 **정확한 지도를 먼저 그리고, 거기에 사용자의 이해를 비춰 보여준다.** 그리고 그 차이로부터 다음에 무엇을 알아봐야 하는지, 지금 가진 앎으로 무엇을 결정할 수 있는지까지 이어 준다.

### 1.1 앎의 상태 (노트·개념 공통)

| 상태 | 뜻 | 들어가는 조건 |
|---|---|---|
| `seen` 들어옴 | 저장만 됨 | 생성 시 |
| `organized` 정리됨 | 구조화됨 | 구조화 완료 |
| `checked` 확인됨 | 원자료와 대조됨 | 대조 완료(자료가 있는 경우) |
| `explainable` 설명할 수 있음 | 사용자가 자기 말로 설명함 | 개념: 사용자가 그 개념을 자기 스파크에서 설명한 문장이 있고 대조에서 Shifted/Missed가 없음. 노트: 대조 Kept 비율 ≥ 설정값(기본 0.8) + 사용자 확인 |

- 상태 변경은 이벤트(`workspace_events`)로 남는다. 뒤로 갈 수도 있다(새 자료와 대조해 어긋나면 `checked` → `organized`).
- v6 5.2 확신도는 그대로 두고, 앎의 상태와 **나란히** 보여준다(확신 높음 + 상태 낮음 = "안다고 생각한 곳일 수 있어요").

### 1.2 MOONS의 역할

| # | 역할 | 하는 일 | 어디서 |
|---|---|---|---|
| 1 | 지도 제작 | 원자료로 정답 지도를 그린다. 적극적이고 정확해야 한다 | 노트(자료) |
| 2 | 받아 적기 | 사용자 덤프를 이해한 그대로 구조화한다. 고치지 않는다 | 노트(스파크) |
| 3 | 대조 | 두 지도를 겹쳐 같은 곳·바뀐 곳·빈 곳을 찾는다 | 노트 비교 |
| 4 | 개념 안내 | 개념 페이지를 채운다: 정의, 분류, 상위·대조·형제 개념 | 개념 |
| 5 | 다음 탐색 | 빈 곳을 보고 무엇을 더 알아볼지, 어느 방향으로 파고들지 구체적 질문과 개념으로 낸다 | 노트 비교, 질문 노트 |
| 6 | 자원 조율 | 결정 앞에서 확실히 아는 것 / 반쯤 아는 것 / 모르는 것을 모아 무엇을 믿고 쓸지, 무엇을 먼저 메울지 정리한다 | 질문 노트 (8장 M5 이후) |

## 2. 원칙 개정 (v6 0장 수정)

v6 0장의 3·4항과 13.5의 "빈칸은 MOONS가 채우지 않는다"는 **사용자 층에만** 적용한다. 층을 나눈다.

| 층 | 원칙 |
|---|---|
| 사용자 층 (내 스파크, 내가 고른 관계·짜임, 내 메모) | 고치지 않는다. 판정하지 않는다. 바꾸는 건 사용자다. (v6 그대로) |
| AI 층 (정답 지도, 개념 페이지, 다음 탐색, 자원 조율) | **끝까지 채운다.** 비워 두거나 사용자에게 미루지 않는다. 대신 모든 내용에 **출처 층**을 붙인다. |

- **출처 층** `layer`: `'user'`(사용자가 쓴 말) · `'material'`(사용자가 넣은 원자료) · `'ai'`(MOONS가 보충한 지식). 화면에서 셋은 항상 구분돼 보인다.
- 사용자 노트의 빈칸은 여전히 사용자가 쓴다. 단, MOONS는 "빈칸이 있다"에서 멈추지 않고 **빈칸이 정확히 무엇인지**(어떤 개념, 어떤 관계, 어떤 질문)를 구체적으로 제시한다(역할 5).

## 4. 탭 구조

내비게이션은 **8개 탭을 4묶음으로** 보여준다. 어느 화면에서든 떠 있는 MOONS 달 버튼으로 대화를 시작할 수 있다. 플래너·임포스터·설정은 탭에서 뺀다.
탭 이름 아래 부제나 설명은 붙이지 않는다(0장 7항). 아래 "한 문장 목적"은 구현 기준이지 화면 문구가 아니다.

| 묶음 | 탭 | 한 문장 목적 | 들어가는 것 | 나오는 것 | 경로 |
|---|---|---|---|---|---|
| 만들기 | 기록 Capture | 생각과 자료를 넣는다 | 스파크, 자료, 폼 | 노트 | `/` |
| 만들기 | 대화 Chat | MOONS와 나눈 대화를 모아 보고, 새 대화를 한다 | 대화 | 대화 노트, 개념, 새틀라이트 초안 | `/chat`, `/chat/:id` |
| 앎 | 노트 Notes | 노트 하나를 깊게 다듬고 내 이해가 맞는지 확인한다 | 노트 | 정리·확인된 노트, 다음 탐색 | `/notes`, `/entries/:id` |
| 앎 | 개념 Concepts | 개념 하나가 무엇인지, 무엇과 어떻게 다른지 안다 | 노트·대화 속 개념 | 개념 페이지 | `/concepts`, `/concepts/:id` (신규) |
| 앎 | 스테이션 Station | 붙잡고 있는 질문을 노트와 개념으로 푼다 | 질문 노트, 끌어온 노트·개념 | 질문 노트(→ 다시 노트가 됨) | `/station`, `/station/:id` (신규, `/compare` 흡수) |

| 함께·확장 | 새틀라이트 Satellite | 필요한 확장을 켜고 끈다 | — | 켜진 기능이 사이드바에 나타남 | `/satellite` (신규) |

### 4.1 기록
- 지금 홈 그대로. 스파크 입력 중 문장을 골라 **`질문으로 열기`** → 질문 노트 생성(`origin: {entryId, sentence}`), 스테이션으로 이동.
- 폼(v6 3장, 구현됨)은 **쓰는 곳**이 기록이다(배너 유지). 폼을 **만드는 곳**은 새틀라이트로 옮긴다. 폼 기능 자체는 그대로 유지한다.

### 4.2 노트
- 목록 + 노트 화면(구조도 · 원문 · 비교, v6 13장 그대로).
- 추가: 구조도·원문에서 **개념에 밑줄**, 누르면 오른쪽에 개념 패널(5.2 요약 + 개념 페이지로 이동).
- 추가: 노트에 **메모** 붙이기.
- 추가: 비교 탭 아래 **다음 탐색** 카드(역할 5): 빈 곳마다 "무엇을 알아볼지"(질문 1개 + 관련 개념 1~3개) + `질문으로 열기`.
- 노트 종류 필터: 스파크 / 자료 / 질문 / 대화.

### 4.3 개념 (신규)
- 목록: 이름, 분류, 앎의 상태, 등장 노트 수. 정렬·필터(분류, 상태, 주제).
- 개념 페이지: 5.2의 모든 필드. 정의와 관계마다 출처 층 표시. **왜소행성**(사용자가 한 번도 자기 말로 설명한 적 없는 개념, 5.2 `unfamiliar`)은 그렇게 표시하고 `설명해 보기`(→ 이 개념을 제목으로 둔 스파크 입력)를 둔다. 사용자가 설명하면 왜소행성 표시가 사라진다.
- 개념 페이지 안의 미니 지도: 이 개념을 중심으로 1단계 이웃 개념(ELK 배치).

### 4.4 스테이션 (신규)
- 질문 노트 목록(상태별) + 질문 노트 화면(5.1 구조).
- 기존 `/compare` 작업대(패널 3개, 하이라이트, 연결, Pinned 대화)는 질문 노트 화면의 **재료 패널**로 들어온다. 질문 없이 쓰는 비교도 남겨 둔다(`/station/compare?ids=`, `/compare?ids=`는 여기로 리다이렉트).
- 질문 노트는 저장되는 순간 노트이므로 노트 탭·내 우주에서도 보인다.

### 4.5 내 우주
- 지금 우주 화면 그대로 + 필터 추가: 노트 종류, 주제, 앎의 상태, 개념 포함 여부.
- 여기서 시작한 대화는 "전체 피드백" 대화가 된다(4.7).

### 4.6 새틀라이트 (신규)
세 갈래. 켜면 사이드바 아래에 나타난다(`settings.satellites: string[]`).
- **연결**: 외부와 주고받기. 이번 범위에서는 자리만. 노션·옵시디언 가져오기와 MOONS 커넥터(4.9)는 다음 단계.
- **도구**: 일정표(지금의 플래너), 임포스터. 기존 기능을 옮기기만 한다(로직 변경 없음). 기본 꺼짐, 단 기존 사용자 중 데이터가 있으면 켜진 상태로 시작.
- **내가 만든 것**: 폼 만들기(지금의 폼 편집기), 대화에서 만든 것(4.7 산출물). 메모: "논문 읽기 폼" 기본 템플릿 후보(참고: Moonlight 리딩 가이드) — 이번 범위 밖.
- 설정은 계정 메뉴로 옮긴다.

### 4.7 대화
- **진입 위치가 맥락을 정한다.** 사용자에게 대화 목적을 따로 고르게 하지 않는다.
  - 노트·개념·질문 노트에서 시작 → 그 대상이 대화에 태그로 남는다(기존 Pinned 맥락 재사용). 대화는 그 대상 화면에서도 보인다.
  - 내 우주에서 시작 → 전체 피드백 대화(저장된 보기·필터가 맥락).
  - 대화 탭에서 빈 대화로 시작 → 자유 대화.
- 대화 탭: 대화 목록(최근순, 태그된 대상·주제로 필터, 검색) + 대화 화면.
- 대화가 끝나거나 사용자가 `정리하기`를 누르면 MOONS가 **대화 노트**를 만든다(`Entry.kind='chat'`). 사용자가 따로 고르거나 확인할 단계를 늘리지 않는다. 대화 노트에 들어가는 것:
  - 무슨 대화를 나눴는지(요약)
  - **다시 찾아볼 것**: 대화에서 나온 자료·근거·출처
  - **더 공부할 것**: 대화에서 나왔지만 사용자가 자기 말로 설명하지 않은 개념(→ 왜소행성으로 개념 탭에 자동 등록)과 열린 질문(→ `질문으로 열기` 가능)
  - 원래 대화 전체(링크)
  - 내부적으로 발화자(사용자/MOONS)는 구분해 저장한다. 대조·앎의 상태 계산에는 사용자 발화만 쓴다. 이 구분은 화면에 별도 절차로 드러내지 않는다.
- 대화 중 만든 것(폼 초안, 정리 틀, 체크리스트 등)은 `대화 산출물`로 저장되고 새틀라이트 "내가 만든 것"에 들어간다. 폼으로 바로 쓸 수 있는 것은 `폼으로 등록`.

#### 4.7.1 탐색 지도 (대화 안 기능)
강의계획서 없이 MOONS와 학습 범위를 함께 잡는 기능. 대화 화면에서 연다(`탐색 지도` 버튼 또는 사용자가 요청).
1. **목적**: 탐색 분야와 목표 수준을 정한다. 쌓인 노트·개념이 적으면 신뢰도 부족을 아이콘(`!`)으로 표시한다.
2. **진단**(데이터가 적을 때): MOONS가 개념별 질문지를 낸다. 개념마다 `설명할 수 있음 / 들어 봄 / 처음` 셋 중 하나를 고른다.
3. **지도**: MOONS가 단원별 개념 지도 초안을 낸다(`layer:'ai'`). 개념마다 사용자의 앎 상태(개념 저장소 + 진단)와 근거 종류를 보인다. `!` 항목(5.6)을 사용자가 모두 확인해야 `지도 확정`이 켜진다.
4. 확정한 지도는 **기준 지도**가 된다: 다음 탐색(6.3)과 개념 페이지의 "아직 다루지 않은 이웃"이 이 지도를 기준으로 계산된다.
```ts
type ExploreMap = { id: string; chatId: string; goal: string; target: string;
  units: { name: string; concepts: { conceptId?: string; name: string; state: 'known'|'heard'|'new'; layer: 'user'|'material'|'ai'; ref?: { entryId: string; sentence: number } }[] }[];
  confirmedAt?: string };   // exploreMaps 컬렉션 (신규)
```
- 대화 노트(5.5)와 같은 대화에서 만들어지면 대화 노트에서 지도로 링크한다.

### 4.8 팀
- 탭으로 둔다. 기본 제공 기능이며, 이후 플랜별로 열린다(`plan` 게이트 자리만 만든다).
- 이번 범위: v6 9.2 / M6 구현 그대로 + 탭 위치 이동.
- 다음 설계(범위 밖): 노션식 협업 — 팀 공유 노트, 팀 개념 사전, 팀 질문 노트, 댓글, 권한. 목적은 "함께 일할 때 같은 이해를 하고 있는지 확인"이다.

### 4.9 MOONS 커넥터 (다음 단계, 설계만)
다른 LLM 채팅(Claude, ChatGPT 등)에서 나눈 대화를 MOONS 안에서 나눈 대화처럼 들여오는 MCP 서버. (참고: 기존 LEET_drill MCP 서버와 같은 방식)
- 도구 초안: `save_chat(title, messages, source)` → 대화 탭에 외부 대화로 저장, 대화 노트 생성(4.7과 같은 처리) / `create_note(kind, text)` / `add_concepts(names, chatId?)` / `save_artifact(name, type, content)` → 새틀라이트 "내가 만든 것" / 읽기: `search_notes`, `get_concept`, `get_question`(바깥 LLM이 내 앎을 참고).
- 인증: Clerk 계정 연결(OAuth).
- 제약: 바깥 채팅에서는 그 LLM이 넘겨주는 내용만 들어온다. "이 대화 전체를 MOONS에 저장해" 같은 요청에 대화 전문을 `messages`로 넘기도록 도구 설명을 쓴다.

## 5. 데이터 (모두 스토어 컬렉션 / 필드 추가. M1 동기화·이벤트 기록이 그대로 적용된다)

### 5.1 질문 노트 — `Entry.kind='question'`
IBIS(쟁점 기반 정보 체계: 질문 → 답 후보 → 근거)에 결정과 남은 것을 더한 구조.
```ts
type QuestionStatus = 'open' | 'working' | 'tentative' | 'closed';
type SubQuestion = {
  id: string; text: string; status: QuestionStatus;
  materials: { entryIds: string[]; conceptIds: string[] };
  decision?: { chosen: string; reason: string; rejected: { option: string; why: string }[]; by: 'user' };
  layer: 'user' | 'ai';            // AI가 쪼갠 하위 질문은 사용자가 채택하기 전까지 'ai'
};
type Question = {
  why: string;                     // 왜 묻게 됐나(어디서 막혔나) — 사용자 말
  status: QuestionStatus;
  subQuestions: SubQuestion[];
  answer?: { text: string; layer: 'user' | 'ai'; at: string };
  origin?: { entryId: string; sentence: number };
};
// Entry에 question?: Question 추가. title = 의문문. body/sentences = why (원문 불변 규칙 적용)
```
- **남은 것**은 저장하지 않고 계산한다: 상태가 `open`인 하위 질문 + 재료 개념 중 `unfamiliar` 개념.
- **과정**은 `workspace_events`에서 이 질문 노트 관련 이벤트만 걸러 재생한다(v6 6.4 재사용).
- AI(역할 5): 질문 노트를 열면 하위 질문 초안과 재료 후보(기존 노트·개념 검색)를 낸다. `layer:'ai'`로 들어오고 사용자가 채택해야 `'user'`.

### 5.2 개념 — `concepts` 컬렉션 (신규)
```ts
type ConceptKind = 'theory' | 'method' | 'tool' | 'term' | 'entity' | 'other'; // 이론·방법·도구·용어·사람/기관·기타
type ConceptRel = 'kind_of' | 'part_of' | 'implements' | 'contrasts' | 'similar' | 'related';
type Concept = {
  id: string;
  name: string;                    // 명사구
  aliases: string[];
  kind: ConceptKind;
  definition: { text: string; layer: 'user' | 'material' | 'ai'; ref?: { entryId: string; sentence: number } }[];
  relations: { to: string; rel: ConceptRel; layer: 'user' | 'material' | 'ai'; ref?: { entryId: string; sentence: number } }[];
  mentions: { entryId: string; nodeId?: string; sentence: number; by: 'user' | 'material' }[];
  state: 'seen' | 'organized' | 'checked' | 'explainable';
  unfamiliar: boolean;             // 계산값: 사용자 스파크에서 자기 말로 설명한 문장이 없음
  createdAt: string;
};
```
- **승격 기준**(구조화 단계 B에서 AI가 판정): 원문이 정의하거나 설명하는 대상 / 여러 명제의 항으로 반복 등장 / 다른 개념과 `kind_of`·`part_of`로 엮임 — 셋 중 하나 이상. 일반어("중요하다", "방법")는 승격하지 않는다.
- **정규화**: 새 노트의 개념 후보를 기존 개념과 대조해 같은 것은 `mentions`에 덧붙이고 별칭을 합친다. 동음이의어는 나눈다(`이름 (뜻 구분)`).
- 개념 페이지의 `layer:'ai'` 정의·관계는 비워 두지 않는다(2장). 최소: 정의 1개, `kind`, 상위 개념 1개(있으면), 대조 또는 형제 개념 1개 이상.

### 5.3 메모 — `memos` 컬렉션 (신규)
```ts
type Memo = { id: string; target: { type: 'entry' | 'concept' | 'question' | 'none'; id?: string }; text: string; createdAt: string };
```
- 원문이 아니다. 구조화·대조 대상이 아니다. `스파크로 올리기` → 새 스파크 노트(메모 원문을 본문으로).
- 기존 비교 화면의 "내 말 메모(자식 노트)"는 그대로 두고, 새 메모와 목록에서 함께 보이게만 한다.

### 5.4 앎의 상태 필드
- `Entry.knowledge?: 'seen'|'organized'|'checked'|'explainable'`, `Concept.state`. 1.1 규칙으로 서버가 갱신하고 이벤트를 남긴다.

### 5.5 대화 노트 — `Entry.kind='chat'`
```ts
type ChatNote = {
  chatId: string; summary: string;              // 무슨 대화였나 (layer 'ai')
  revisit: { text: string; ref?: string }[];     // 다시 찾아볼 것
  study: { conceptIds: string[]; questions: string[] }; // 더 공부할 것
  artifacts: string[];                           // 대화 산출물 id
};
// Entry에 chat?: ChatNote 추가. sentences = 대화 중 사용자 발화(원문 불변 규칙 적용)
```
- `chats` 스레드에 `tags: {type:'entry'|'concept'|'question'|'galaxy', id?}[]`, `noteId?` 추가.
- 대화 산출물: `artifacts` 컬렉션 `{id, chatId, name, type:'form'|'outline'|'checklist'|'text', content, createdAt}`.

### 5.6 출처 층
- AI가 쓴 모든 문장 필드에 `layer`를 둔다. 화면: `user` = 기본 글꼴, `material` = 원문 인용 스타일, `ai` = 달 아이콘 + 흐린 색.
- **`!` 확인 필요**: `layer:'ai'` 중에서 **원자료·사용자 노트 근거(`ref`) 없이 AI 지식만으로 쓴 것**에만 `!` 아이콘을 덧붙인다. 원자료에서 끌어온 AI 정리(`ref` 있음)에는 붙이지 않는다. 사용자가 확인하면 `!`가 사라진다(확인 기록은 이벤트로 남김).
- 상태 표시는 글자보다 아이콘으로 한다(채움 / 빈 곳 / 원문 근거 / `!` / 사용자 확정, 앎: 앎 / 들어 봄 / 처음).

## 6. 구조화 v3 — 정확한 지도

v6 13장(짜임 · 관계어 · SOLO · 신호)은 유지한다. 바꾸는 것은 **한 번의 호출로 지도를 그리게 하던 방식**이다.

### 6.1 원자료 → 정답 지도 (역할 1)
단계를 나누고 단계 사이에 검증 가능한 중간 데이터를 둔다. 단계마다 별도 호출 + 구조화된 출력.

| 단계 | 입력 → 출력 | 규칙 |
|---|---|---|
| A 명제 추출 | 문장들 → `Claim{id, subj, rel, obj, sentence[], kind:'explicit'|'implied'}` | **원문 근거(sentence 번호)가 없으면 명제 없음.** `implied`는 담화 표지(그러므로·반면·예컨대 등)가 근거일 때만 |
| B 개념 정규화 | 명제의 항 → 개념 후보 → 승격·병합(5.2) | 기존 `concepts`와 대조. 별칭 병합, 동음이의어 분리 |
| C 관계 타입 | 명제 → 엣지 `rel` | v6 13.2 관계어 목록에서만 고른다(닫힌 목록). 자유 서술 금지 |
| D 척추 선택 | 섹션별 짜임(v6 `frame`) → 지배 관계 | 지배 관계 엣지 = `role:'spine'`, 나머지 = `role:'cross'`(흐리게) |
| E 배치 | 노드·엣지·섹션 → 좌표 | **ELK(`elkjs`) layered**, 섹션 = 그룹(중첩), `hierarchyHandling: INCLUDE_CHILDREN`. LLM은 좌표를 정하지 않는다 |
| F 자기 검증 | 지도 → 지표 | 9.2의 커버리지·충실도·고아 개념을 계산해 `analysis.quality`에 저장. 기준 미달이면 A~C를 1회 재시도 |

- `Edge`에 `role: 'spine'|'cross'`, `claimIds: string[]` 추가. 기존 `label`, `rel`, `relBy`는 유지.
- 재생(설명 순서): 척추를 따라 위상 정렬하되 **정의가 사용보다 먼저** 오게 한다. 스텝 = 항목·엣지 하나 + 근거 원문 한 문장. 코멘트 달 아이콘(v6 13.5)이 스텝 단위로도 붙는다(북마크 → 그 지점 대화).

### 6.2 덤프 → 내가 이해한 지도 (역할 2)
- A~E는 같되 **고치지 않는다.** 추출 프롬프트에 "복원·교정 금지"를 명시하고, 평가는 별도 패스로 분리한다.
- 사용자가 접속어로 이은 관계는 `asserted_rel`(사용자가 주장한 관계)로 기록하고, 타당성은 `assessment`(별도 필드, 기본 숨김 레이어)에 둔다.
- **용어 사용 프로파일**: 같은 단어가 덤프 안에서 두 뜻으로 쓰이면 개념 후보를 `이름@뜻1`, `이름@뜻2`로 나누고 표시한다.
- **비약**: A에서 C로 바로 건너뛴 연결은 `gap: true` 엣지로 표시한다.

### 6.3 대조와 다음 탐색 (역할 3·5)
- 두 지도는 B단계의 **같은 개념 ID**로 정렬한다. 문장 층 대조(Kept/Shifted/Added/Missed)는 v6 그대로.
- 다음 탐색 카드: Missed·Shifted·`gap`·`unfamiliar` 개념마다 `{question: string, concepts: conceptId[], why: string(근거 원문 인용 번호)}`. 비워 두지 않는다.

### 6.4 PDF 첨부 (M3 선행 작업)
- 기록 탭 자료 입력에 **파일 끌어다 놓기 + 파일 선택**. PDF부터.
- 원본 파일은 보관(기존 object storage)하고, 원문 보기에서 열 수 있게 한다.
- 추출 텍스트가 원문이다(원문 불변 규칙 적용). **제목·섹션 구분·쪽 번호를 살려서** 추출한다(제목은 짜임 판정 신호).
- 문장마다 쪽 번호를 남긴다: `Anchor`에 `{kind:'page'; page:number}` 추가. 원문 인용·근거 표시에 쪽을 함께 보인다.
- 텍스트 층이 없는 스캔 PDF는 이번 범위에서 처리하지 않고 그렇다고 알린다(OCR은 다음 단계).

### 6.5 비용 — 품질 먼저
- R&D 기간에는 **비용 때문에 품질을 줄이지 않는다.** 모델·단계·재시도는 9.2 기준 통과를 우선해 고른다.

### 6.6 모델 선택과 사용량 기록 (품질·비용 비교용, 구현됨 2026-10-24)
- 공급자: **OpenAI · Anthropic · Google Gemini**. 키는 Railway 변수 `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`. 키가 없는 공급자의 모델은 고를 수 없고, 골라 둔 상태면 기본값(OpenAI)으로 돌아간다. 임베딩과 음성 받아쓰기는 OpenAI 고정.
- **운영자 계정**: Railway 변수 `MOONS_OPERATORS`(쉼표로 구분한 이메일 또는 Clerk 사용자 ID). 운영자는 하루 한도가 없고, 설정 → **AI 모델**에서 **단계별로** 모델을 고른다(구조화 · 비교 · 감정 태그 · 대화 · 사진으로 폼 · 임포스터 · 기타). 목록에 없는 모델은 `공급자:모델ID`로 직접 입력한다(예 `gemini:gemini-3.7-flash`, 가격 미상으로 기록).
- 구조화 v3를 구현할 때 A~D 단계와 개념 페이지·다음 탐색·대화 노트·탐색 지도를 `ai/catalog.ts`의 `STEPS`에 단계로 추가한다.
- **사용량 기록**: 모든 AI 호출이 `ai_calls`에 한 줄씩 남는다(사용자, 단계, 작업, 공급자, 모델, 입력·출력·캐시 토큰, 추정 비용, 걸린 시간, 성공 여부). 설정 → AI 모델 아래에 최근 30일 단계·모델별 합계(전체 / 나)가 보인다. API: `GET /api/ai/usage?days=30`(운영자만).
- 같은 노트를 모델을 바꿔 다시 구조화하면 분석 기록(`analyses`)에 모델 이름과 함께 남아 나란히 비교할 수 있다.
- `scripts/eval-structure.mjs`는 `--model` 인자로 같은 골든 세트를 모델별로 돌려 지표·비용을 표로 낸다(M3).

## 9. 평가 기준 (청사진)

### 9.0 골든 세트 (M3 전에 먼저 만든다)
`docs/golden/`에 둔다. **자료와 그 자료를 읽고 쓴 스파크를 짝으로** 준비해, 한 세트로 지도 제작·받아 적기·대조를 같이 검사한다.
**골든 세트 자료와 스파크는 사용자가 만든다**(구현 기간 동안 병행). 에이전트는 채점 스크립트와 G1(부록 A) 기준 확인까지 하고, 세트가 들어오면 정답 지도 초안을 만들어 사용자 검수에 넘긴다. 정답이 필요한 9.2 지표는 검수가 끝난 뒤 실행한다.

**짧은 짝 세트 (정답 지도 전체 검수)** — 자료 300~1500자

| # | 자료 | 스파크 | 왜 |
|---|---|---|---|
| G1 | 없음 | 부록 A 덤프 | 덤프 충실도·다의어·비약 |
| G2 | LEET 추리논증 지문 | 그 지문을 읽고 쓴 내 정리 | 논증형 짜임, 담화 표지 |
| G3 | 설명문(교과서·위키 한 단락) | 내 정리 | 분류형 짜임, 개념 승격 |
| G4 | 실제 회의록 | 내 정리 | 실사용, 나열·결정 혼합 |
| G5 | 논문 초록 | 내 정리 | 원인→결과, 전문 용어 |
| G6 | G3와 같은 개념이 나오는 다른 자료 | 없어도 됨 | 개념 병합·별칭·동음이의어 |

**긴 자료 (부분 검수)** — 실제 사용 길이

| # | 자료 | 스파크 | 정답 범위 |
|---|---|---|---|
| L1 | 논문 PDF 전문 1편 | 내 정리 | 섹션별 짜임 전체 + 핵심 개념 목록 + 무작위 섹션 2개의 정답 지도 |
| L2 | 긴 회의 녹취·문서 1개 | 내 정리 | 위와 같음 |

- 스파크는 일부러 틀리게 쓰지 않는다. 평소대로 쓴 실제 오류가 들어 있어야 한다.
- 긴 자료는 정답 지도 전체를 검수하지 않는다. 대신 정답이 필요 없는 지표(근거 없는 엣지, 고아 개념, 배치, 흔들림)는 전체에 적용하고, 정답이 필요한 지표는 검수한 범위에만 적용한다. 섹션 사이 개념 병합(같은 개념이 앞뒤 섹션에서 한 개념으로 합쳐지는가)과 처리 시간·비용을 따로 적는다.
- 각 정답 파일: 명제 목록(원문 번호 포함), 개념 목록(이름·별칭·kind), 엣지(관계어·spine/cross), 섹션별 짜임.

### 9.1 화면·구조 (M1~M2)
- [ ] 내비게이션 탭이 정확히 8개(4묶음)이고 이름이 3장·4장 표와 일치한다(한/영).
- [ ] 화면 어디에도 사용자에게 '노드'라는 말이 보이지 않는다(i18n 문자열 검색으로 확인).
- [ ] 옛 경로(`/universe`, `/compare`, `/planner`)가 깨지지 않는다(리다이렉트 또는 유지).
- [ ] 새틀라이트에서 일정표를 끄면 사이드바에서 사라지고, 켜면 데이터가 그대로 보인다.
- [ ] 새로 추가된 화면 설명·안내 문구가 없다(0장 7항).
- [ ] 기존 테스트 전부 통과. 특히 원문 불변·동기화 테스트.

### 9.2 지도 품질 (M2~M4) — 골든 세트 대비 자동 채점 스크립트 `scripts/eval-structure.mjs`

| 지표 | 정의 | 기준 |
|---|---|---|
| 근거 없는 엣지 | `claimIds`가 비었거나 근거 문장이 원문에 없는 엣지 수 | **0** |
| 명제 커버리지 | 정답 명제 중 지도 엣지로 표현된 비율 | ≥ 0.85 |
| 충실도 | 지도 엣지 중 정답 명제에 대응하는 비율 | ≥ 0.85 |
| 관계어 정확도 | 대응된 엣지 중 관계어가 정답과 같은 비율 | ≥ 0.75 |
| 짜임 일치 | 섹션별 짜임이 정답과 같은 비율(신호 없는 섹션은 `null`이어야 정답) | ≥ 0.8 |
| 개념 승격 | 정밀도 / 재현율 | 각각 ≥ 0.8 |
| 개념 병합 | G3+G6에서 같은 개념이 한 페이지로 합쳐진 비율, 잘못 합쳐진 수 | ≥ 0.9 / 0 |
| 고아 개념 | 어떤 엣지에도 없는 개념 수 | 0 |
| 개념 페이지 채움 | AI 층 최소 필드(5.2) 다 채운 개념 비율 | 1.0 |
| 배치 | 항목 겹침 / 그룹 밖으로 나간 항목 | 0 / 0 |
| 덤프 교정 금지 (G1) | 추출 단계 출력에서 사용자 말이 아닌 표현으로 바뀐 항목 수 | 0 |
| 덤프 비약·다의어 (G1) | 사람이 표시한 비약·다의어 중 잡아낸 비율 | ≥ 0.7 |
| 다음 탐색 | Missed·Shifted·gap 중 카드가 붙은 비율 / 카드에 개념이 1개 이상 있는 비율 | 1.0 / 1.0 |

- 기준 미달 지표는 실패 사례(골든 # · 문장 번호 · 기대 · 실제)를 보고서에 나열한다.
- 같은 입력을 3회 돌려 지표의 흔들림(최대-최소)도 적는다. 0.1 넘게 흔들리면 실패로 본다.

### 9.3 스테이션 (M5)
- [ ] 스파크 문장에서 `질문으로 열기` → 질문 노트 생성, `origin` 보존, 제목이 의문문.
- [ ] 부록 B 예시를 손으로 입력했을 때 같은 구조(하위 질문 4개, 결정 1개, 남은 것 계산)가 화면에 나온다.
- [ ] 남은 것이 저장값이 아니라 계산값이다(하위 질문을 닫으면 즉시 줄어듦).
- [ ] 질문 노트가 노트 탭·내 우주에서도 보이고, 재료 노트·개념과 선으로 이어져 있다.
- [ ] AI가 낸 하위 질문은 채택 전까지 `layer:'ai'`로 구분돼 보인다.

### 9.4 대화 (M6)
- [ ] 노트·개념·질문 노트에서 시작한 대화에 그 대상 태그가 남고, 그 대상 화면에서도 대화가 보인다.
- [ ] 대화 탭에서 태그·주제로 필터가 된다.
- [ ] `정리하기` → 대화 노트가 생기고, 요약·다시 찾아볼 것·더 공부할 것이 **모두 채워져** 있다(빈 항목이면 "없음"이 명시됨).
- [ ] 더 공부할 것의 개념이 개념 탭에 왜소행성으로 들어가 있다. 사용자에게 추가 확인 절차를 요구하지 않는다.
- [ ] 대화 노트의 `sentences`가 사용자 발화만으로 이뤄져 있다.
- [ ] 대화 중 만든 폼 초안이 새틀라이트 "내가 만든 것"에 보이고 `폼으로 등록`이 된다.

## 부록 A. 골든 G1 — 덤프 원문 (사용자 작성, 2026-10-24)

> 1. 지금 저 한장 환경이 평면적인 한장이 아니라 웹 내에서 한장이니까 네 말대로 시각화를 할 때는 필터를 걸어서 기준 잡아서 하면 되는 부분이잖아? 그럼 우선은 이론적으로만 보면 한 개념 단어를 설명하는 노드들을 만들어놓고 마치 나무위키처럼 무언가를 설명하기 위한 개념 단어를 각각 다 구조화 시킨 다음, 그 구조들이 들어있는 페이지를 갖고 다시 개념을 설명하는 방식이어야 하는데,
> 인간이 넣는 정보는 '단어'가 아니라 특정 상황에서 어떤 내용을 보고 이해하고 있는지야.
> 당연히 그 내용 안에 들어있는 단어들을 인간은 전부 정확히 이해하고 있는 건 아니고, MOONS에서 하려는 건 최소한 내가 정리한 내용에 내포되어있는 개념단어 만큼은 설명할 수 있게 하려던 거였어.
> 여기에는 2가지 문제가 있어
> 1) AI는 인간이 dump한 내용을 바탕으로 인간이 이해한 대로 구조화를 시켜야 하는데, 이때 인간은 부정확한 단어 사용 및 여러 논리적 오류들을 범한다. 이 상황에서 AI를 어떻게 굴려야 지금 인간이 말한 단어와 인간이 이해한 상관관계를 볼 수 있을지 모르겠다
> 2) AI는 원자료를 분석해서 구조화시킬 수 있어야 하는데, 이때 필요한 것은 노트 형태로 정리되는 것보다도 각 개념간 지도를 볼 수 있도록 정확히 내용을 그리는 것이다. 이때 주입된 정보는 모두 참이라 가정하고 정리되어야 하는데, 어떻게 설계해야 관계도가 이해될지 모르겠다.
> -> 기술적으로 보완한다면 마치 개념을 AI가 지금 막 설명해주는 것처럼 최종 페이지를 한눈에 볼 수도 있지만 동시에 어떻게 이 페이지의 개념도가 그려지는지 재생을 눌러서 따라가면서 이해하는 것도 하나의 방식일 것이다. 보다가 넘어가는 부분이 이해가 안되는 지점에서 북마크를 해놓고 AI에게 다시 묻는 방식을 쓸 수 있으면 보완 가능하지 않을까 싶다.
>
> 우선 이게 되어야 인간 이해가 정확했는지 비교하는 게 될텐데 지금은 이 단계의 정확도가 떨어져서 아직 그 다음단계로 못넘어가고 있었어.
>
> 그리고 지금 설계에 묻는 건 충분히 구현 가능한 영역이고 현재도 되는 영역인데, 정답을 알고 있는채로 물어봐야 그 물음이 의미가 있잖아. 그런데 너나 클로드코드나 인간에게 판단의 여지를 맡긴다에만 집중해서 AI가 할 일을 부실하게 설계하고 있다는 게 문제야.
> 지금은 가시적으로 볼 수 있는 잘 정리된 구조도 만드는 것에 집중해줘

검수 시 확인할 것: "노드"·"페이지"·"한장"이 여러 뜻으로 쓰임(다의어), "AI를 어떻게 굴려야"에서 "상관관계"로 건너뛰는 지점(비약 후보).

## 부록 B. 질문 노트 예시 (9.3 수동 입력용)

```
Moons 구조도는 왜 피상적으로 나올까?                 [working]
why: AI 시각화가 너무 피상적이라 비교 단계로 못 넘어감
├─ 원자료로 정답 지도를 어떻게 정확히 그리나?        [tentative]
│   재료: 개념 — 명제 추출, 원문 근거, 관계 타입, ELK, dagre, 계층형 그래프 레이아웃
│   결정: 배치는 ELK / 이유: 그룹(섹션) 중첩 지원 / 버림: dagre — 그룹 표현 불가
├─ 덤프를 내가 이해한 대로 어떻게 구조화하나?        [open]
├─ 두 지도를 어떻게 비교하나?                        [open]
└─ 개념을 노트 밖에 어떻게 쌓나?                      [tentative]
    재료: 개념 — 개념 저장소, 명사구 규칙
answer: AI가 한 번에 그리게 해서. 단계를 쪼개고 근거를 강제한다.
남은 것(계산): open 하위 질문 2개 + unfamiliar 개념(ELK, dagre 등)
```
개념 페이지 확인용: `ELK`(kind: tool, implements → 계층형 그래프 레이아웃), `dagre`(tool, implements → 계층형 그래프 레이아웃, contrasts ELK: 그룹 미지원), `계층형 그래프 레이아웃`(theory/method, 별칭: 스기야마 방식, contrasts → 힘 기반 레이아웃).
